# 抽取作業程序

從受追蹤文件建立新 claim 列的程序。回填（判定既有列）見 `runbooks/backfill.md`。

**必讀**：`ledger/SCHEMA.md` §2、§6，`ledger/TOPICS.md`，
`STATUS.md` §3.18，`CLAUDE.md` 第 6 條。

---

## 1. 批次劃分

**以來源文件的節為單位，一次一節或數個相鄰節。** 不跨文件。

抽取批次與回填批次不同：回填依 `section`（主題）劃分，抽取依來源文件的節劃分。
理由是抽取需要原文的上下文，而上下文是按文件組織的。

每批開始前記錄該節在原文的行號範圍，結束時確認整段都掃過。

---

## 2. 逐句掃描

對該節的每一個句子問：**這句話是否可獨立證偽？**

- 是 → 候選 claim
- 否（純敘述、比喻、過渡句） → 略過
- 含兩個以上可獨立證偽的宣稱 → **拆成多條候選**，見 SCHEMA §6

〔注意〕表格與條列項每一列都要單獨看。既有帳本中相當比例的問題列來自表格，
因為表格的一列在視覺上是一個單位，容易被整列抽成一條 claim。

---

## 3. 決定 `section`（v7 起）

**查 `ledger/TOPICS.md`，取該主張主題所屬的節點。**
不得照抄來源文件的節號——三份受追蹤文件的節號互相衝突。

判斷順序：

1. 這條主張講的是什麼**主題**（不是它出現在哪裡）
2. 在 `TOPICS.md` 找最貼切的節點
3. 找不到 → **停，不要造節號**。記入本批報告的「待建節點」，該批結束後一併提案

易混淆的分界，`TOPICS.md` 內有註記，這裡重複最常撞的一組：

| 分界 | 判準 |
|---|---|
| `4.2.1` vs `5.6.x` | 主詞是分子或通路 → `4.2.1`；是器官疾病進程或臨床終點 → `5.6.x` |
| `4.1` vs `4.1.1`–`4.1.3` | 肝素酶作為降解機制之一 → `4.1`；肝素酶本身的分子生物學 → `4.1.x` |
| `5.5` vs `5.7` | 標記物本身的性能 → `5.5`；篩檢流程與技術平台 → `5.7` |
| `6.1` vs `6.3` | 治療原則的轉向 → `6.1`；具體藥物或標靶 → `6.3` |

---

## 4. 檢查是否已有列

**新增前必須掃描既有列。** 依 SCHEMA §2 的認定規則：

- 同一主張已有列 → **追加 `source_ref`**，不建新列
- 數值相同但解剖歸屬不同 → **建新列**（保留可偵測的漂移）
- 數值不同 → 建新列

掃描方式：以**數值**為鍵搜尋整份 `claims.csv`，不要只看同一個 `section`——
跨文件重複正是本專案要偵測的東西，而它們在抽取前不會落在同一個 `section`。

---

## 5. 撰寫 `statement`

依 SCHEMA §6。抽取階段最容易出錯的四項：

1. **模態詞逐字保留**（`STATUS.md` §3.18）。
   原文的「未必／可能／傾向於／在部分情況下」不得省略或換成全稱。
   模態承載的是主張的**範圍**，範圍被放大等同於數值被改寫。
   已發生過一次：`2.4-precursor-insufficient` 的「未必能」被寫成「無法」，
   查證時被自己的證據推翻。
2. **數值逐字相符**（`CLAUDE.md` 第 4 條）。範圍不得取中位數，
   單位不得換算，約略詞（「約」「達」）保留。
3. **時間形容詞與未具名權威一律移除**（SCHEMA §6，v4）。
   「2025 年最新共識」「國際公認」改寫為可證偽的形式，
   原措辭寫進 `note` 作為查證對象。
4. **不得為劑量、途徑、療程建 claim**（`CLAUDE.md` 第 6 條）。
   `TOPICS.md` §6.3 的內容大量觸及此項。

---

## 6. 填寫其餘欄位

| 欄位 | 抽取階段的值 |
|---|---|
| `claim_id` | `{section}-{slug}`，slug 用英數與連字號 |
| `claim_type` | `fact` / `mechanism` / `therapeutic` / `epidemiology` |
| `tier`、`evidence` | **留空** |
| `status` | `unverified` |
| `priority` | 見下 |
| `last_checked` | **留空** |
| `note` | 原文的承載措辭、可疑之處、與既有列的關係 |
| `source_ref` | `{目錄}/{檔名}#{來源節號}`，此處用**真實**節號 |

`priority` 判準：帶具體數值或宣稱高證據等級（RCT、共識、指南）→ `high`；
機制性敘述 → `med`；背景與定義 → `low`。

---

## 7. 收尾

1. 依 `claim_id` 重新排序整份 CSV
2. 驗：列數、欄數全為 11、無 BOM、無 CRLF、排序正確
3. 寫批次報告到 `reports/extraction/`，含：
   - 掃描範圍（檔案與節號）
   - 淨新增列數、追加 `source_ref` 的列數、略過的句子數
   - **待建節點**（若有）
   - 抽取時發現的原文問題（供日後開修訂單）
4. 更新 `STATUS.md` §1 計數與 §2 批次表

---

## 8. 已知的失效模式

- **模態被強化**（`STATUS.md` §3.18）——抽取環節特有,見 §5.1
- **整列表格被抽成一條 claim**——見 §2
- **只在同一個 `section` 內查重**——見 §4。跨文件重複在抽取前不同 `section`
- **自行造節號**——`heparanase.md` 收錄時的章節重編就是這樣做的，
  代價是三份文件的座標系全面碰撞，直到 121 列都寫完才發現

〔推論〕最後一項的特徵是**在第二份資料進來之前完全不可見**。
抽取階段的錯誤多屬此型：當下看起來合理，要等到有東西跟它比對才會顯現。
所以本程序把「查既有列」與「查 TOPICS」放在撰寫 `statement` **之前**——
先做比對，再寫內容。
