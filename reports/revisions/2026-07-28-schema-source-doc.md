```
提案日期: 2026-07-28

提出來源: 多文件收錄前的架構評估
schema_version: 2 → 3（若核准）
狀態: 待人工核准
```

---

## 1. 問題

`ledger/claims.csv` 的 97 列全部抽自 `source/glycocalyx_v3.md`。
`claim_id` 的格式為 `{section}-{slug}`（如 `2.1.1-extreme-11um`），
其中 `section` 隱含「v3 的第 2.1.1 節」——**文件身分沒有欄位承載，是靠慣例默認的**。

〔推論〕一旦 `source/` 有第二份文件，三件事會壞：

1. **節號碰撞**。第二份文件也會有 §2.1、§5.1，`claim_id` 無法區分
2. **無法回答「這條主張出自哪」**。網頁的稽核層與行內標記都需要這個資訊定位
3. **同一主張跨文件出現時會產生重複列**。這是最嚴重的一項

第 3 點已經實際發生。`糖萼層_Glycocalyx_生理.md` 與 `v3` 共有至少 9 組相同數值
（85%/78%、72%/81%、80%/75%、77%/70%、OR 2.04、OR 5.06、HR 2.10、11 μm、0.5-5 μm）。
若照現行 runbook 逐節抽 claim，這 9 組會各自產生第二列。

〔推論〕兩列描述同一件事，就會有兩個 `status`、兩份 `evidence`、兩段 `note`。
下一次某條被判 `contested` 時，只有一列被更新，另一列繼續顯示 `verified`——
**這正是 `retraction watch` 提案擔心的「過期 verified」，只是來源不是撤稿而是分身。**

---

## 2. 設計上的關鍵取捨

〔推論〕核心問題是：**ledger 的一列代表什麼？**

| 定義 | 後果 |
|---|---|
| 一列 = 一份文件的一個片段 | 同一主張在三份文件出現就有三列。判定要做三次，且會不同步 |
| 一列 = 一個知識單位（主張本身） | 同一主張只有一列，`source_doc` 記它出現在哪些位置。判定一次，三處共用 |

〔推論〕本專案的產出是「這個數字可不可信」，不是「這份文件寫了什麼」。
**判定應綁 claim，不綁文件。** 後者才是正確定義。

副作用是好的：網頁的行內標記在三份文件的三個位置指向同一個 `claim_id`，
讀者點開看到的是同一份判定與同一段 note，不會出現「A 文件說已驗證、B 文件說查無出處」。

## 3. 選項

### 選項 A：新增 `source_ref` 多值欄，`claim_id` 不變（建議）

新增一欄 `source_ref`，值為 `;` 分隔的多個 `{doc}#{section}`：

```
source_ref = glycocalyx_v3#5.5;intake/2026-07-28-糖萼層生理#表1
```

- `{doc}` 為 `source/` 下的路徑去掉副檔名
- `{section}` 為該文件內的節號或可辨識的位置標籤（表格用 `表N`，無節號文件用行號區間）
- 既有 97 列一次性回填為 `glycocalyx_v3#{現有 section 欄的值}`，可機械化完成
- `claim_id` **完全不變**，既有的三份批次報告與兩份修訂提案的引用不受影響
- `section` 欄保留，語意改為「主要出處的節號」＝ `source_ref` 第一個 token 的節號

**優點**：

- 不動 `claim_id`，零回溯成本
- 一條 claim 一列，判定不會分身
- 多值欄的格式與既有 `evidence` 欄一致（`;` 分隔、第一個為主要），agent 不需學新語法
- 網頁的行內標記可直接由 `source_ref` 反查該渲染哪些位置

**缺點**：

- 回填 97 列需要一次 commit（機械化，風險低）
- 「同一主張」的判斷需要人。數值相同但條件不同（例如 v3 說腎絲球 11 μm、生理.md 說腦部 11 μm）
  算不算同一條？見 §5 的認定規則

### 選項 B：`claim_id` 加文件前綴

`v3:2.1.1-extreme-11um` / `phys:結構-11um`。

**優點**：一眼看出出處。
**缺點**：破壞既有 97 個 `claim_id`，三份批次報告、兩份修訂提案、CHANGELOG 的引用全部要改。
且沒有解決重複列問題——反而讓重複變成正式制度。

### 選項 C：一文件一個 ledger

`ledger/claims-v3.csv`、`ledger/claims-phys.csv`。

**優點**：完全隔離。
**缺點**：跨文件統計要合併三個檔；同一主張的判定不同步問題完全沒解決，只是搬到檔案層。
STATUS §1 的帳本狀態失去意義。

---

**建議採 A。**

## 4. 若核准，具體改動

### 4.1 `ledger/SCHEMA.md` §3 欄位表

在 `section` 之後新增一列：

```markdown
| N | `source_ref` | 是 | 主張在原始文件中的出現位置。多值，`;` 分隔。見 §3.N |
```

新增小節：

```markdown
### `source_ref`

格式：`{doc}#{section}`，多個位置以 `;` 分隔，**第一個為主要出處**。

- `{doc}`：`source/` 下的相對路徑去掉 `.md`（例：`glycocalyx_v3`、`intake/2026-07-28-糖萼層生理`）
- `{section}`：該文件內的節號。文件無節號時，用可辨識的位置標籤（`表1`、`L122-131`）

同一主張在多份文件出現時，**只建一列**，把所有位置寫進 `source_ref`。
不得為了區分文件而複製列。

`section` 欄的值必須等於 `source_ref` 第一個 token 的節號部分。
```

### 4.2 `ledger/SCHEMA.md` §6 statement 修改規則

補一句：

```markdown
當一條 claim 的 `source_ref` 含多份文件，且各文件的敘述不完全相同時，
`statement` 應寫成涵蓋各版本的形式，差異寫入 `note`。
若差異大到無法涵蓋（不同血管床、不同族群、不同終點），拆成兩列，
各自的 `source_ref` 只記自己的出處，並在兩列的 `note` 互相標示對方的 `claim_id`。
```

## 5. 「同一主張」的認定規則（本提案一併請求核准）

〔推論〕這是選項 A 唯一需要人工判斷的地方，不寫明會在第二份文件收錄時立刻出問題。

**視為同一條**（追加 `source_ref`，不建新列）：

- 數值、指標、族群、終點四者皆相同，僅措辭不同
- 數值相同、措辭不同，但可判定為同一來源的轉述（例如兩份文件都寫 85%/78% 且都歸給 syndecan-1 預測敗血症死亡）

**視為不同條**（各自建列，`note` 互相標示）：

- 數值相同但歸屬不同（例：11 μm 在 v3 歸腎絲球、在生理.md 歸腦部）
- 同一指標但數值不同（例：syndecan-1 敏感度 85% vs 90%）

〔推論〕第二組看似該合併，實則不能。**歸屬或數值的漂移本身就是需要被追蹤的證據**
（見 STATUS §3.6）。合併會把這項資訊抹掉，而它正是判斷「有無原始出處」的線索。
兩列各自查證，`note` 互相指認，才留得下這條軌跡。
