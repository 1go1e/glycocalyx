## 1. 問題

三份受追蹤文件各有一套從 `1.1` 起算的節號，互相衝突：

```
v3          33 節   1.1 – 6.2
heparanase  64 節   1   – 7.4     與 v3 重疊 23 個節號
axis        13 節   1.1 – 1.5     與 v3 重疊  2 個節號
```

重疊的 23 個節號中，**19 個已被既有 121 列佔用**。語意上完全不相干：

| 節號 | v3（既有 121 列所依據） | heparanase／axis |
|---|---|---|
| `1.2` | 線粒體—糖萼軸 | axis: 線粒體—糖萼軸的生理機制 |
| `2.2` | 區域異質性 | 糖尿病特異性破壞糖萼的機制 |
| `4.1` | 酶介導降解 | 糖尿病神經病變的時間序 |
| `5.4` | 缺血再灌注損傷 | 臨床實際應用建議 |
| `6.1` | 從數量到質量的治療轉向 | heparanase 基因與蛋白結構 |

### 為什麼不能靠「`claim_id` 不會撞」帶過

`claim_id` 確實不撞（slug 不同）。壞掉的是 **`section` 欄本身的功能**。SCHEMA §2 明載：

> `section` 是**主題座標**，不是位置指標。批次劃分（STATUS §4）與
> `claim_id` 排序都依賴它把同主題的條目聚在一起。

抽取後 `section=5.4` 會同時裝著 v3 的缺血再灌注、heparanase 的臨床應用建議、
以及 2026-07-31 拆出的兩條 S1P。**「跑 §5.4 這一批」將不再是一個有意義的動作**，
而那是 STATUS §4 排批次的唯一依據。

### 根因

`heparanase.md`（42 節 → 1–7.4）與 `axis.md` 都在收錄時做過章節重編，
兩次都只考慮文件內部結構，未對照 `v3` 已佔用的座標。
當時三份文件沒有任何共用的 claim，問題看不出來。

〔推論〕這是 schema v5 的同一個失效放大版。v5 處理「intake 檔沒有節號」，
本案是「三份檔各有一套且互相衝突」。兩者的正解也相同：
**`section` 取主題座標，位置資訊交給 `source_ref`。**

## 2. 選項

### 選項 A：設立正規主題樹，所有文件的 claim 取其主題所屬的正規節號（建議）

`section` 一律取正規樹節號，`source_ref` 承載真實位置。
等於把 v5 的 intake 例外一般化到所有文件。

- 優點：與 v5 的既有精神一致，**不動任何既有列**（v3 的節號即正規樹起點）
- 優點：跨文件去重與批次劃分都保住——同主題的列聚在一起，這是本專案的核心功能
- 缺點：v3 的樹涵蓋不了 heparanase 的全部內容，需擴充（見 §3.2，新增 11 個節點）
- 缺點：抽取時每條需做一次主題歸位判斷，比照抄節號慢

### 選項 B：每份文件保留獨立命名空間（`hp:5.4`、`ax:1.2`）

- 優點：機械、零判斷
- 缺點：`claim_id` 正規表示式 `^[0-9](\.[0-9]+)*-...` 不允許冒號，須一併改
- 缺點：**跨文件去重的聚類直接失效**。同一主張在 v3 與 heparanase 各出現一次時
  會落在兩個座標，違背 SCHEMA §2「一條主張，一列」的設計目的

### 選項 C：重編 `heparanase.md` 與 `axis.md` 的節號到保留區段（7.x、8.x）

- 優點：`section` 仍等於 `source_ref` 的節號，SCHEMA §2 不必加例外
- 缺點：要改原始檔，`axis.md` 已重編兩次
- 缺點：**治標**。同主題的列仍散在 v3 的 1.2 與 axis 的 7.2，聚類一樣不成立

**建議採 A。**

## 3. 若核准，具體改動

### 3.1 正規樹獨立成檔：新建 `ledger/TOPICS.md`

**不要讓正規樹繼續隱含在 `v3.md` 的標題裡。**

目前的正規樹事實上就是 v3 的節號，但它從未被寫下來過。若日後 v3 因標註或改寫
而動到標題編號，121 列的 `section` 會全數失去依據，而**沒有任何機制會發現**。

`ledger/TOPICS.md` 為唯讀規格檔，格式與 SCHEMA.md 同級：

```markdown
# 正規主題樹

```
topics_version: 1
last_updated: (核准日期)
```

> 本檔定義 `claims.csv` 的 `section` 欄可用值。
> agent 不得自行新增節點；需要新節點時寫提案到 reports/revisions/。

| 節號 | 主題 | 起源 |
|---|---|---|
| 1.1 | 範式轉移：超越靜態屏障 | v3 |
| ... | | |
```

「起源」欄記錄該節點來自哪份文件，方便日後追溯。

### 3.3 `ledger/SCHEMA.md` §2 的 `source_ref` 小節

現行：

```markdown
`section` 欄的值必須等於 `source_ref` 第一個 token 的節號部分。

**例外：主要出處位於 `intake/` 之下時**，`section` 取該主張主題所屬的受追蹤文件節號，
而非 intake 檔的位置標籤。
```

改為：

```markdown
`section` 欄的值必須是 `ledger/TOPICS.md` 所定義的正規主題樹節號，
取該主張**主題所屬**的節點，**不必等於** `source_ref` 的節號。

理由：`section` 是主題座標，不是位置指標。受追蹤文件各有自己的節號體系且互相衝突
（v3 與 heparanase 有 23 個節號重疊而語意不同），
若照抄來源節號，同一個 `section` 會裝進不相干的主張，
使批次劃分（STATUS §4）與跨文件去重失去依據。
位置資訊由 `source_ref` 承載，不重複。

`ledger/TOPICS.md` 未涵蓋的主題，**不得自行造節號**——
寫提案到 `reports/revisions/`，核准後遞增 `topics_version`。
```

原本的 intake 例外併入上述通則，不再單獨列出。

## 5. 連帶影響

- **既有 121 列不需回填。** v3 的 33 個節號原樣成為正規樹節點，`section` 值不變
- **STATUS §4 的批次劃分**：正規樹擴充後，`5.6.x` 與 `6.3` 會是抽完後最大的兩個群
- **`runbooks/`**：抽取程序需新增一步「查 `TOPICS.md` 決定 `section`」，
  建議在核准後與 SCHEMA 同一個 commit 補
- **`CLAUDE.md`**：必讀清單需加入 `ledger/TOPICS.md`
- **`topics_version` 與 `schema_version` 分離**：主題樹會隨新文件收錄而擴充，
  但那不是 schema 變更。兩者各自遞增，`TOPICS.md` 的變更記在自己的檔頭與 CHANGELOG
