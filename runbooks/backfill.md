# 回填作業程序（Backfill Runbook）

```
版本: 1
適用: 將 ledger/claims.csv 中 status=unverified 的條目回填證據
前置: 必須先完整讀過 ledger/SCHEMA.md
```

---

## 1. 目標

把 97 條 `unverified` 主張，逐條檢索文獻後轉為
`verified` / `partial` / `contested` / `unsupported` 之一。

**這不是「找到支持文獻」的任務，是「確定每條主張的證據狀態」的任務。**
`unsupported` 是完全合格的產出，不是失敗。回填結束時若 `verified` 比例過高，
應懷疑判定標準過寬。

---

## 2. 批次規則

- **一批 5-8 條，且限定同一 `section`。**
  每條需要 2-4 次檢索，一批約 20-30 次工具呼叫，這是單一 session 內能維持判定品質的上限。
- 同章節可共用背景脈絡，減少重複檢索。
- 依 `priority` 降冪處理：先做完所有 `high`，再做 `med`，`low` 最後。

**建議起手批次**：`5.1-sdc1-cutoff-40`、`5.1-sdc1-sens-spec`、`5.1-sdc1-or-204`。
這三條互相關聯（很可能出自同一篇），且是全表風險最高的數值。先做這批，
可以同時驗證整套流程與判定標準。

---

## 3. 單條處理流程

### 步驟 1 — 拆解 statement

列出這條主張中所有**可獨立查證的要素**：

- 實體（分子、疾病、族群、血管床、物種）
- 關係（升高／降低／預測／導致／相關）
- **所有數值**，逐一列出

範例（`5.1-sdc1-cutoff-40`）：
```
實體: Syndecan-1, 血漿, 敗血症, 死亡率
關係: 預測
數值: 40 ng/mL
未指定: 族群（成人？ICU？敗血性休克 vs 敗血症）、檢測平台
```

「未指定」那一項要特別記下來——它通常就是最後判成 `partial` 的原因。


**改寫檢查（依 SCHEMA §6）。** 拆解時若 statement 含以下任一項，先改寫再檢索：

- 時間形容詞（「最新」「近年」「截至 2025 年 11 月」）→ 移除，時間入 `note`
- 未具名的權威性宣稱（「國際共識」「新典範」「臨床標準」）→ 改寫為可指名的形式，
  例如「〔某學會〕〔某年〕立場聲明將 X 列為 Y」。檢索時就查這份聲明是否存在；
  查不到即 `unsupported`，不因原文語氣強烈而放寬

### 步驟 2 — 檢索

依序嘗試，找到足夠證據即停：

1. **Europe PMC**（涵蓋最廣，含預印本與全文）
2. **PubMed**（MeSH 詞精確檢索）
3. **bioRxiv / medRxiv**（僅當前兩者無果，且主張標示為近年新發現）
4. **ClinicalTrials.gov**（僅 `claim_type=therapeutic`）

**若該列 `section` 為 `6.3.1`，本步驟不適用——改用 §3A 替換 1 的順序。**

檢索式從步驟 1 的實體組合而成。若首次檢索超過 200 筆，加上限定條件；
若為 0 筆，逐步放寬並記錄放寬的過程。

### 步驟 3 — 核對數值（不可省略）

對步驟 1 列出的**每一個數值**，在候選文獻的摘要或全文中找到對應處，**逐字比對**。

- 原文 `40.4 ng/mL`，statement 寫 `40 ng/mL` → **不一致**，記為 `partial`
- 原文 `approximately 85%`，statement 寫 `85%` → 可接受，但 `note` 須註明原文為近似值
- 原文 `OR 2.04 (95% CI 1.51-2.76)`，statement 寫 `OR 2.04` → 一致
- 找不到該數值的出處 → 不得推估或換算，該數值視為未獲支持

### 步驟 4 — 判定

```
找到直接支持的原始研究？
├─ 否 → 找到的只有敘述性綜述？
│        ├─ 是 → 循其引用追原始研究。追到則回到上一層；
│        │        追不到 → status=unverified，note 記錄該綜述 PMID
│        └─ 否 → status=unsupported，note 記錄檢索範圍與關鍵字
└─ 是 → 同時找到反駁文獻？
         ├─ 是 → status=contested
         └─ 否 → 所有數值逐字相符，且研究條件與 statement 範圍一致？
                  ├─ 是 → status=verified
                  └─ 否 → status=partial，note 寫明差異在哪
```

**與上述並行的一支**（不影響 `status`，但不得省略）：

```
找到的文獻既不支持也不反駁，但與該主張的來源相關？
└─ 是 → 依 SCHEMA §4 加 ~ 前綴寫入 evidence，
         note 必須寫明不對位的是哪一個維度
         （量測對象／量測方法／量綱／介入／族群或血管床／時間或劑量條件）
         未直接取得、僅由他篇引述得知者不得填 ~，只記入 note
```

〔注意〕這一支最常在判 `unsupported` 的列上觸發，且那正是它價值最高的時候——
`unsupported` 說「站不住腳」，`~` 說「知道為什麼站不住腳」。
判完 `unsupported` 就收工，會把該列資訊量最高的一筆丟掉。

**拆列檢查**：若步驟 1 拆解出的要素顯示這一列含兩個以上可獨立證偽的宣稱，
依 SCHEMA §6「拆列程序」先拆再判。已判定才發現者，判定照常寫入，拆列另案處理。

額外約束（來自 SCHEMA §2）：
`claim_type` 為 `epidemiology` 或 `therapeutic` 的條目，
若唯一證據來自體外或動物研究，**不得判為 `verified`**，一律 `partial`。

### 步驟 5 — 寫入

更新該列的 `tier`、`evidence`、`status`、`last_checked`、`note`。
`last_checked` 一律更新為當日，**即使結果是 `unsupported`**。

若本次查證過程中發現該主張也出現在其他 `source/` 文件，在 `source_ref` 追加該位置
（格式見 SCHEMA §2）。追加前先確認符合 SCHEMA §2「認定規則」的「同一條」標準——
歸屬不同或數值不同時**不得追加**，應另建一列並在兩列的 `note` 互相標示。

`note` 的撰寫要求：寫下**下一個人需要知道的事**，不是過程流水帳。

- 好：`原文 cutoff 40.4 ng/mL，族群限 ICU 成人敗血性休克；statement 需補族群限定`
- 差：`搜尋了 Europe PMC 找到幾篇相關文獻`

## 3A. 註冊類主張的回填（`6.3.1`）

**適用於 `section` 為 `6.3.1` 的列。** 這些主張斷言的是**註冊系統或藥證系統的當下狀態**
（某藥處於某階段、某藥在某地區已核准、目前無任何藥物獲准），
不是文獻中的發現。§3 的流程對它們有四處失效，逐一替換：

### 替換 1 — 檢索順序倒過來

§3 步驟 2 的順序（Europe PMC → PubMed → 預印本 → ClinicalTrials.gov）
對本節點是反的。前三個來源查不到「Phase II 中止」或「歐洲已核准」。改為：

1. **ClinicalTrials.gov**（NCT 編號、`Recruitment Status`、`Last Update Posted`）
2. **EU Clinical Trials Register / CTIS**（歐洲試驗，NCT 常缺）
3. **藥證資料庫**：EMA、FDA Drugs@FDA、各國主管機關（核准類主張的唯一權威來源）
4. **公司公告與投資人簡報**（開發終止／停滯類主張常只見於此）
5. Europe PMC／PubMed（僅用於**佐證**，不作為狀態的主要依據）

〔注意〕來源 4 的可靠性遠低於前三者，但對「開發停滯」類主張常是唯一來源。
使用時 `note` 必須寫明是公司自述而非第三方登記。

### 替換 2 — `tier` 留空

`in_vitro`／`animal`／`human_obs`／`rct`／`meta`／`review` 六個值沒有一個能描述
「NCT 編號顯示該試驗狀態為 terminated」。**本節點的 `tier` 一律留空**，
不要因為主張提到 Phase III 就填 `rct`——那是在描述被斷言的對象，不是斷言的證據等級。

### 替換 3 — `unsupported` 的語意不同，且需要三段式檢索

對文獻類主張，`unsupported` 是「這個宣稱站不住腳」。
對註冊類主張，查不到往往只代表**該試驗從未登記**，或**登記在非英語註冊系統**
（中國 ChiCTR、俄羅斯、伊朗、印度 CTRI），本節點至少 5 列涉及這些地區。

因此判為 `unsupported` **之前**必須做完三段：

1. 藥物名 + 所有已知代號（見 `6.3.2` 的代號對應列——這是它應該先回填的原因）
2. 至少一個非英語註冊系統（ChiCTR 或 WHO ICTRP 跨庫檢索）
3. 該藥開發者的公司公告

三段都空才寫 `unsupported`，且 `note` 必須列出查過哪三個系統。
**只查了 ClinicalTrials.gov 就寫 `unsupported` 是錯的**，
這會把「我們沒查到」誤記成「原文站不住腳」，而兩者在月報中的意義完全相反。

〔前提〕本替換**僅適用於「查無記錄」型**。若已取得**正面記錄且內容與 statement 相反**
（如註冊資料明載 Phase 1／多發性骨髓瘤，而 statement 稱 Phase II／胰腺癌），
那是**反駁**不是查無——直接以 `!` 標記該記錄即可，不需跑三段式。
已經有記錄了，再跑三段式只是重複確認同一件事。判別法見 `queries.md` §8.9。

### 替換 3B — 全稱、否定與計數型主張：先判可判定性，再決定要不要檢索

「沒有任何 X」「唯一的 X」「所有 X 都…」「至少 N 個 X」這類主張，
在檢索**之前**必須先回答一個問題：**這個主張的論域可以列舉嗎？**

不先問，就沒有終止條件——三段跑完永遠可以有第四段，而每一段都查不到，
每一段也都無法證明下一段查得到。

#### 三類與各自的處置

**第一類：論域可列舉（登記制）**

論域落在藥證資料庫或試驗註冊資料庫之內。這兩者都是**登記制**——
要臨床可用就得有藥證，要做人體試驗就得登記，因此集合有邊界。

處置：**先把論域定義寫進 `note`，再列舉，再判定。**

論域定義的寫法必須讓下一次重驗照同一個範圍跑，例如：

```
論域：各國藥證資料庫中，以 heparanase 抑制為機制主張的已核准藥物。
不含以其他機制核准而恰具 heparanase 抑制活性者。
```

寫下論域即是宣告終止條件。列舉完該論域就結束，不再擴大檢索。

**第二類：存在命題（「至少 N 個」）**

「至少 20 個進入臨床試驗」**可證真不可證偽**。找到 20 個就成立；
找不到只代表沒找到，不代表不存在。

處置：**只求證真，湊到即停。**檢索目標是湊數而非窮盡，
與全稱否定的策略正好相反。湊到 → `verified`；湊不到 → `partial` 或 `unsupported`，
且該判定為**終局**，`note` 寫明「已檢索到 N 個，未達所稱數量」，不留待續。

不要為了證偽一個存在命題而擴大檢索——那是無底的。

**第三類：論域不可列舉**

論域跨越無揭露義務的範圍。典型例子：

- **IND-enabling 階段**——遞件前，法律上無公開揭露義務，
  公開來源**結構性地不存在**這份資料
- 未登記的院內試驗、非英語系統中未進 WHO ICTRP 的項目

處置：**零檢索，直接判定。**`note` 寫「論域不可列舉」並說明理由。
跑三段式是純粹浪費——不是查不到，是不可能查到。

#### 為什麼要分這三類

`unsupported` 目前混了兩種性質完全不同的東西：

| | 將來可能翻案 | 月報意義 |
|---|---|---|
| 查了沒有 | 是 | 原文可能有誤，也可能是我們沒查到 |
| 不可能查到 | **否** | 原文的宣稱形式本身無法查證 |

後者永遠不會翻案，卻和前者用同一個 status 值。
`note` 必須寫明是哪一種，否則重驗時會對第三類重跑一次註定失敗的檢索。

#### 順序上的好處

同一份列舉常可一次清掉多列。建議**先做列舉，再逐列比對**，
而不是逐列各自檢索——後者會把同一份清單查上好幾遍。

### 替換 4 — 必須寫 `stale_after`

依 SCHEMA §13 的三檔間隔，於首次脫離 `unverified` 時與 `last_checked` 同時寫入。
判斷該用哪一檔，看 statement 斷言的是哪一類狀態：

- 含「沒有任何」「唯一」「僅有」→ 6 個月
- 某藥現處於某階段／已核准／進行中 → 12 個月
- 開發終止／試驗中止／停滯 → 24 個月

**漏寫會被 SCHEMA §9 檢查 (2) 攔下**，commit 前跑得到。

### 額外要記的一件

註冊狀態帶日期。查到「Last Update Posted: 2024-03」時，`note` 要寫下**該狀態的時間戳**，
不只寫狀態本身。下一次重驗時，判斷「有沒有變」靠的是這個日期而不是記憶。

## 4. 必須停下來問人的情況

遇到以下任一情況，**不要自行判定**。在該列 `note` 標記 `NEEDS-REVIEW`，
`status` 維持不變，並寫進本批次報告，然後繼續處理下一條：

1. 找到的文獻**推翻**了原 statement 的方向（不只是數值不同，而是結論相反）
2. 同一數值在兩篇以上文獻中出現但**互不引用**，無法判斷是否同源
3. statement 涉及的是**尚未被明確命名或研究的概念**，找不到對應詞彙
4. 需要修改 statement 的語意才能與文獻相符，而該列已是 `verified`
5. 檢索結果顯示 `source/glycocalyx/v3.md` 有**內部矛盾**（見 claims.csv 中已標記的厚度與 GAG 佔比問題）

## 5. 批次產出

每批次結束時：

1. 更新 `ledger/claims.csv`（依 `claim_id` 重新排序後存檔）。
   新增列必須填 `source_ref`；建列前先以數值為鍵掃描既有列，
   命中且符合 SCHEMA §2「同一條」標準時，改為在既有列追加 `source_ref`，不建新列。
   主要出處位於 `intake/` 之下時，`section` 依 SCHEMA §2 例外取主題所屬的受追蹤文件節號
2. 寫入 `inbox/YYYY-MM-DD-{section}.json`：保留所有檢索的原始回傳，不做刪減
3. 寫入 `reports/backfill/YYYY-MM-DD-{section}.md`：

```markdown
# 回填批次 {section} — YYYY-MM-DD

處理 N 條： verified X / partial Y / contested Z / unsupported W / needs-review V

## 判定摘要
- {claim_id}: {status} — {一句話理由}

## NEEDS-REVIEW
- {claim_id}: {為何無法判定}

## 對原文件的修訂建議
- {section}: {建議如何修改，附 claim_id}

## 本批次有效的檢索詞
- {實際命中的關鍵字組合}
```

最後一節請確實填寫。這些實測關鍵字構成 `ledger/queries.md`
的監測檢索式——它們是這個階段的副產品，但價值不低於主產出。

**寫完報告後，同步更新 `ledger/queries.md`**：把本批次的檢索式併入其 §2，
新浮現的通則寫進 §1。查過但無果的檢索式記入 §4——
那記錄的是「這樣查過、沒用」，可避免下一批重複嘗試。
開始檢索前先讀該檔 §1 與 §2.1 的定錨值表。

4. 依 SCHEMA §10 格式提交一個 commit

---

## 6. 絕對禁止

- 憑記憶或推測寫出 PMID / DOI / NCT 編號。識別碼只能來自檢索工具本次回傳的結構化欄位
- 修改 `source/` 下的任何檔案。所有修訂建議一律寫入 `reports/`
- 刪除 `claims.csv` 中的任何列
- 為了讓數字好看而放寬判定標準
